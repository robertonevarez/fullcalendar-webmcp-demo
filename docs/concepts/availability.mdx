# Availability and Slot Computation

Availability calculation in Protocol Tooling is deterministic, rule-based, and timezone-aware.

---

## The Availability Query (`AvailabilityQuery`)

When an agent requests availability, it submits:

```json
{
  "service_id": "svc_ac_diagnostic",
  "start_date": "2026-09-01",
  "end_date": "2026-09-03",
  "postal_code": "78704",
  "time_preference": "morning",
  "preferred_resource_id": "res_hvac_maria"
}
```

---

## Computation Pipeline

For each day in the requested date range, the scheduler executes the following pipeline:

```text
1. Discretize Day into 15-Minute Grid (00:00, 00:15, ..., 23:45)
   │
2. Convert Local Business Time to UTC
   │
3. Filter by Business Working Hours
   │
4. Filter by Time Preference (Morning: < 12:00, Afternoon: 12:00-17:00, Evening: > 17:00)
   │
5. Check Resource Requirement Satisfiability
   ├─ Verify resource working hours
   ├─ Check resource capabilities
   ├─ Exclude existing confirmed appointments
   └─ Exclude blocked times (breaks, maintenance)
   │
6. Construct Unique Slot Token (slot_id)
   └─ Encodes: service_id + start_time + allocated resource IDs
```

---

## Anatomy of a `slot_id` Token

Availability slots are not raw database IDs; they are deterministic tokens that capture the exact resource allocation snapshot:

```text
slot_<service_id_hash>_<unix_timestamp>_<resource_alloc_hash>
```

When an agent later calls `create_appointment(slot_id: ...)`, the backend re-validates that:
1. The slot is within the valid TTL window (default 30 minutes).
2. The allocated resources remain unbooked by competing transactions.
3. No newly added blocked times overlap the requested interval.

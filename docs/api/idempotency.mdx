# Idempotency & Concurrency

To ensure that network retries by autonomous AI agents do not result in double bookings or duplicate charges, Protocol Tooling enforces **cryptographic request idempotency**.

---

## The Idempotency Key

Clients supply an idempotency key either via:
* The `Idempotency-Key` HTTP Header
* The `idempotency_key` field in the request JSON body

---

## Idempotency Scopes & Hashing

When `create_appointment` is received, `BookingService` builds an idempotency scope:

```ts
export function buildIdempotencyScope(
  businessId: string,
  key: string,
  payload: Record<string, unknown>
): { scopeKey: string; payloadHash: string } {
  const normalized = JSON.stringify(payload, Object.keys(payload).sort());
  const payloadHash = createHash('sha256').update(normalized).digest('hex');
  const scopeKey = `${businessId}:${key}`;
  return { scopeKey, payloadHash };
}
```

---

## Deduplication Logic

1. **Exact Match (Cached Return)**: If a request arrives with an identical `scopeKey` and `payloadHash`, the server returns the existing confirmed `Appointment` immediately without creating a second record.
2. **Conflict Detection (`IDEMPOTENCY_CONFLICT`)**: If a request arrives with the same `scopeKey` but a different `payloadHash` (e.g. changing the customer name or slot ID), the server rejects the request with `IDEMPOTENCY_CONFLICT`.
